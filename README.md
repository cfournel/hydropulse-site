# gethydropulse.com

Static site for the HydroPulse Wear OS app, published via GitHub Pages at
<https://gethydropulse.com/>. It is both the app's public site and its SEO
surface: one page per hydration topic, per language, plus the privacy policy
used as the Play Console policy URL.

The app itself lives in [hydropulse-wearos](https://github.com/cfournel/hydropulse-wearos),
which is private. This repo is public because GitHub Pages on a private
repository requires a paid plan — that is the only reason it is split out, and
it is why nothing here may carry a key, a keystore or an unreleased plan.

## The privacy policy lives at `/privacy/`

The Play Console policy URL points at <https://gethydropulse.com/privacy/>. If
that path ever moves, Play breaks silently, so treat it as a fixed address.

The policy text is generated from `PRIVACY_BODY` in `build.py`; its source of
truth is `docs/PRIVACY_POLICY.md` in the app repo — keep the two in sync when
the policy changes. Same for `TERMS_BODY` and `docs/TERMS_OF_SERVICE.md`. That
sync is the one real cost of separating the repos: nothing enforces it, so a
policy change has to be made in both places by hand.

## Layout

```
index.html                     English home
hydration/<slug>/              English topic pages
fr/  fr/hydratation/<slug>/    French
es/  es/hidratacion/<slug>/    Spanish
privacy/                       Privacy policy (English, shared by all languages)
terms/                         Terms of service (English, shared)
assets/site.css                The only stylesheet
assets/badges/<lang>.png       Official Google Play badges
assets/screens/*.webp          Watch captures, from the app repo's store-assets/
assets/favicon.svg             Generated by build.py from the same droplet as the header
assets/favicon-{16,32}.png     Raster fallbacks, rendered by make_favicons.sh
assets/apple-touch-icon.png    180px, home-screen icon
favicon.ico                    Root fallback; without it browsers 404 and log it
sitemap.xml  robots.txt  404.html  CNAME
```

Every page is generated. Do not hand-edit the HTML — edit `content.py` and rebuild.

## Building

```bash
python3 build.py
```

No dependencies beyond the standard library. `build.py` owns the template,
canonical URLs, reciprocal `hreflang` alternates, breadcrumbs, JSON-LD and the
sitemap; `content.py` owns every word of copy, keyed by language. Regenerated
files are committed — GitHub Pages serves them directly, there is no build on
the Pages side, so **a change to `content.py` is not live until you rerun
`build.py` and commit the result.**

## Auditing

```bash
python3 audit.py                     # indexability checks, all languages, no deps
python3 audit.py --lighthouse        # + Lighthouse on a sample: home + 1 topic per language
python3 audit.py --lighthouse --all  # every page (~26 runs, several minutes)
python3 audit.py --live              # against gethydropulse.com instead of the build
```

Exits non-zero on a failure, so it can gate a deploy. Run it after every
`build.py`.

Two halves, because no single tool covers both. **Lighthouse** (Google's own,
driven headless against the installed Chrome via `npx`) scores performance,
accessibility, best practices and SEO per page — but its SEO category is
generic: it checks that a page *can* be indexed, and has no idea that
`/fr/hydratation/oublier-de-boire-au-bureau/` and `/hydration/forgetting-to-drink-water-at-work/`
are the same page in two languages. **The static checks in `audit.py`** cover
exactly that gap — reciprocal `hreflang` sets, canonicals pointing at their own
language, sitemap coverage, duplicate titles or descriptions across languages,
`<title>` and description lengths, one `<h1>`, valid JSON-LD, no broken internal
links. That is the half that breaks silently: none of it is visible in a browser
and all of it costs rankings.

Baseline at the time of writing: 100 performance / 100 accessibility / 100 best
practices / 100 SEO on mobile emulation, every language, with no warnings.

## Deploying

The site is the repo root, so GitHub Pages serves it with no build step:
Settings → Pages → Source = "Deploy from a branch", branch `master`, folder
`/ (root)`. A push to `master` is the deploy.

`CNAME` pins `gethydropulse.com`. **Deleting or changing it takes the site — and
with it the Play Console policy URL — offline.** The domain needs GitHub Pages'
four apex `A` records (and the matching `AAAA` set) at the registrar.

`.github/workflows/audit.yml` runs `build.py` and `audit.py` on every push and
fails if the committed HTML is stale or the SEO wiring is broken. It does not
deploy — Pages does that itself — it exists to stop a broken build from
becoming what Pages serves.

## Adding a language

1. Copy an existing language block in `content.py` (`EN`, `FR`, `ES`), translate
   it, and set `code` / `base` / `topic_dir` / slugs.
2. Append it to `LANGS`.
3. Download that language's Google Play badge into `assets/badges/<code>.png`.
4. `python3 build.py`, `python3 audit.py`, commit, push.

The `TOPICS` keys must stay identical across languages — `hreflang` alternates
are matched on those keys, not on slugs, so a missing key breaks the alternate
set for that topic. The slugs themselves should be the natural search phrasing
in each language, not transliterations of the English ones.

Note that the app's own UI is English-only. The site is translated because
search demand is per-language; `ui["app_lang_note"]` says so under every Play
badge, and no copy claims a localised app. If the app is ever localised, drop
that note.

## Screenshots

`assets/screens/*.webp` come from `store-assets/screenshots/` in the app repo,
downscaled from 480×480 to 400 and converted:

```bash
convert ../hydropulse-wearos/store-assets/screenshots/2-home.png \
        -resize 400x400 -quality 84 assets/screens/home.webp
```

Two things keep them from costing anything: every `<img>` carries its intrinsic
`width`/`height`, so the grid never reflows as they load (CLS stays 0), and every
one is `loading="lazy"`, so none of them is the LCP element.

The captures are English-only, so the same four files are shared across all three
languages — alt text and captions are localised, the pixels are not.

## Favicon

`build.py` writes `assets/favicon.svg`; `./make_favicons.sh` rasterises it into
`assets/favicon-{16,32}.png`, `assets/apple-touch-icon.png` and `favicon.ico`.
Run the script after any change to `FAVICON_SVG`, and commit what it produces.

The tab icon is the droplet **filled**, without the pulse trace that the header
mark carries inside it. That is deliberate: at 16px a 1.4px stroke lands on about
one pixel and the interior detail becomes noise, so the silhouette is the only
thing that survives — and the silhouette is what makes the tab findable in a
strip of twenty. Both come from `DROPLET_PATH` in `build.py`, so the tab and the
wordmark cannot drift apart.

**Do not rasterise it with `convert favicon.svg out.png`.** ImageMagick delegates
SVG to `rsvg-convert`, and when that binary is absent it falls back to its own
renderer, which drops these paths and hands you a blank dark square with no
error and a plausible file size. That is exactly how the first version of this
site shipped with an invisible favicon. `make_favicons.sh` drives headless
Chromium instead — the engine that will actually display the icon.

`favicon.ico` at the root is not decorative: without it browsers request it
anyway, get a 404 and log a console error, which costs a Lighthouse
best-practices point.

## The Google Play badge

`assets/badges/{en,fr,es}.png` are Google's own localised "Get it on Google Play"
badges, downloaded from `play.google.com/intl/<locale>/badges/`. Google's badge
guidelines require the artwork unmodified — no recolouring, cropping or
redrawing — so `build.py` emits it as an `<img>` and the CSS only sizes it.
Falling back to the English badge on a French page is worse than it looks: the
badge is the one element on the page a visitor recognises before reading
anything.

## Google Search Console

Verify the domain, then submit `sitemap.xml`. Nothing about a new site's indexing
is automatic, and Search Console is the only place that tells you which pages
Google actually kept, in which language, and which queries reach them.

1. **Domain property, DNS TXT record** (preferred). Add the TXT record at the
   registrar. It covers every subdomain and both schemes, and no template change
   can lose it. Nothing to commit here.
2. **URL-prefix property, meta tag.** Put the token in `SITE["search_console"]`
   in `content.py`, rebuild, commit; `build.py` emits the
   `google-site-verification` meta tag on every page. Leave the value empty when
   using DNS.

Then submit `https://gethydropulse.com/sitemap.xml`, and resubmit after adding a
language. Expect weeks, not days, before the per-language pages appear in the
coverage report.

## SEO notes

- Each topic page targets one intent in one language ("water reminder app for
  Wear OS", "combien d'eau boire par jour", "señales de deshidratación"), with an
  FAQ block marked up as `FAQPage` and a `MobileApplication` block carrying the
  Play price.
- The seven topics split deliberately: three product/device queries that convert
  (`wearos`, `sport`, `heat`), three informational queries with real volume that a
  hydration app can answer honestly (`howmuch`, `signs`, `work`), and one that
  explains the differentiator (`heartrate`). The informational pages are what
  earn links; the product pages are what convert them.
- Every page declares a canonical URL and a full reciprocal `hreflang` set
  including `x-default` (English). The sitemap repeats the alternates per URL.
- No analytics, no third-party scripts, no cookies — deliberately, so the site
  matches the privacy claim the app makes. That also means traffic data comes
  from Search Console alone.

## Health claims

Every page carries the same two non-negotiable blocks, emitted by `build.py`
(`sources` and `privacy_block`): where the model's methodology comes from, and
that HydroPulse is a wellness tool producing an estimate, not a medical device.
Copy that softens or drops the disclaimer, or that promises a clinical outcome
("prevents dehydration", "tells you when you are dehydrated"), is both untrue and
a Play policy problem for a health-adjacent app. The `signs` page is the one to
watch — keep it descriptive, and keep the "when to see a doctor" answer in it.
